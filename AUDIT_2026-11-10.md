# Kitty repo audit — 2026-11-10

Audited at commit `725646f` (branch `main`, clean tree). Nothing was changed, built or run: every
finding comes from reading the code.

## How to read this

- **Confidence.** *Confirmed* means the faulty path was traced end to end in the code.
  *Plausible* means the code is as described but the failure depends on platform behaviour I
  did not reproduce (noted in the row).
- **Severity** is my estimate of user impact: High = visibly wrong behaviour in an ordinary
  workflow, Medium = wrong in a less common workflow or on one platform, Low = rare, cosmetic,
  or self-healing.
- **Coverage.** The repo is about 179,000 lines of source excluding the frozen V1 engine, so
  this was not a line-by-line read of everything.
  - Read in full: the Rust core's startup, lifecycle, health, engine attach, app-key, memory,
    streaming, approvals, notifications, session and prompt modules; `chatStore.ts`; the message
    list and markdown rendering; the engine's chat routes, replay buffer, event hub and
    summarizer; the Android turn and download services.
  - Sampled by targeted search: the rest of the Rust core (`config`, `windows`, `commands/*`,
    `models`), the rest of the engine (agent loop, storage, MCP, scheduler, providers), the
    three tool plugins and the two memory engines.
  - Not read: `plugins/bigtiny_rust/` (frozen V1), tests, `tools/`, CSS.
  - The sampled areas carry many regression comments from earlier audits and I found little
    there; a finding absent from this list is not proof the code is clean.

# 7. Plan: long-running tasks ("runs")

A plan, not an audit finding. The goal is for one request, such as "build an annotated
bibliography of 80 sources on X", to run for hours and millions of tokens without the user
re-prompting, on a self-hosted model with a modest context window.

## 7.1 The problem today

- A turn is one growing context. Every tool result stays in it until the turn ends.
- When the context nears the window, the wrap-up valve withdraws the tools and tells the model
  to finish (`WRAPUP_SYSTEM_MESSAGE`, `agent/loop_.rs:750`, applied around line 3195). The turn
  ends with the work incomplete.
- Compaction only runs *after* a turn (`loop_.rs:4121-4134`), so it cannot help a turn in flight.
- Nothing starts the next turn. The user has to say "continue", and the model has to rediscover
  where it was from a compacted summary that was not designed to carry a work queue.

## 7.2 What already exists and will be reused

| Part | Where | Role in a run |
|------|-------|---------------|
| Detached turns | `routes/jobs.rs`, `storage/jobs.rs`, `run_turn_and_wait` | A segment of a run is a turn with no client attached. |
| Specialists with per-source fan-out | `specialists/server.rs:249-301`, `agent/orchestrator.rs` | One fresh context per work item, with a required answer shape. |
| Step budget and extension tool | `request_more_steps`, `MAX_STEPS_CEILING` (`loop_.rs:683-693`) | Per-segment limit. |
| Scratchpad, document handles, search offload | `kitty-tools`, `kitty-web` | Keep large tool output out of the context. |
| App event stream | `server/app_events.rs`, Kitty's `lifecycle/app_events.rs` | Progress and approvals for a run nobody is watching. |
| Scheduled-run approvals | "denied after 10 minutes unanswered" | The model for unattended approval policy. |
| Android turn service | `TurnService.kt` | Keeps the process alive during a segment. |

## 7.3 Design

**A run** is a durable record in the engine: a goal, a ledger of work items, an output location,
budgets, and a status. It belongs to one chat (its parent session) and one app.

**The ledger** is the source of truth. Each item has an id, a short description, a status
(`todo`, `doing`, `done`, `failed`, `skipped`), an attempt count, and a small result (for the
bibliography: the citation and annotation, or a pointer to where it was written). The model
changes the ledger only through tools, so the engine always knows what is left.

**A segment** is one turn of the run. Its prompt is built from the stable head, the goal, a
compact view of the ledger (counts, the next few `todo` items, the last few results), and
nothing else from earlier segments. A segment ends when its context or step budget is nearly
used, or when the ledger has no open items.

**The driver** is a small loop in the engine. After each segment it reads the ledger and either
starts the next segment, stops because the run is finished, or stops because a limit or a stall
was hit. This is the piece that replaces the user typing "continue".

**Workers** are specialists. For collection work the segment hands items to a specialist with
per-item fan-out; each worker reads its pages in its own context and returns only the small
result. The parent's context grows by a few hundred tokens per item, whatever the pages cost.

**Long-horizon mode** is the user-facing name for a run. It starts in one of two ways:

- *The model chooses it.* Every ordinary turn is offered one loop-only tool,
  `start_long_horizon(goal)`. A model that judges the request too large for one turn calls it;
  the turn ends there and the run begins with planning. The tool's description is fixed text,
  so offering it does not disturb the prompt cache.
- *The user forces it.* A message that begins with `/longhorizon` followed by the request
  starts a run directly. Kitty strips the prefix and calls `POST /api/runs`; the model is not
  asked whether it wants one.

Either way it is a run inside the chat it was started from, not a different kind of session
(core rule 6 still holds).

**Plan confirmation** works like Claude Code's plan mode. The first segment is a planning
segment: the model may read, search and inspect, but its write-class tools are withheld and the
only way it can finish is by submitting a plan (the ledger items, the output location, and the
approach in a few sentences). The run then waits in `awaiting_approval`. Nothing is executed
until the user approves. The user can approve, edit the items (remove, reword, add), ask for a
revised plan with a note, or cancel. Approval is recorded on the run, so a resumed run does not
ask again.

**Segments are visible.** Each segment is an ordinary turn in the user's chat, shown in the
transcript with its tool calls and its text, the same as any other turn. The run card sits
above them as the summary and the controls. Because a long run adds many segments to one chat,
the transcript collapses finished segments to one line each ("Segment 7: 9 items done") that
expands on click; the virtualized message list already handles the length.

```
user request ──> plan segment ──> ledger (N items)
                                    │
        ┌───────────────────────────┘
        ▼
   driver loop:  segment k ──> hands items to workers ──> results into ledger + output file
        │             ▲                                             │
        └─ open items? ┴──────────── yes ◄──────────────────────────┘
                 │ no
                 ▼
          verify segment ──> gaps become new items, or the run completes
```

## 7.4 Rules the design must keep

- **Engine changes are additive and app-scoped** (the engine is shared and stays on 2.x): new
  routes under `/api/runs`, new tables, new loop-only tools. No existing route changes shape.
- **Kitty stays a client.** The driver, ledger and budgets live in the engine. Kitty starts,
  shows, pauses and cancels runs.
- **No chat/agent mode** (core rule 6). A run is something a chat starts, shown inside that
  chat; it is not a different kind of session.
- **Errors are states** (core rule 7). A stalled or over-budget run is a status with a reason
  and a Resume button, not a toast.
- **No silent re-execution.** Jobs are deliberately not re-queued after a restart because a turn
  may have had side effects. A run resumes at the *item* level: `doing` items go back to `todo`
  with their attempt count raised, and items are written to be safe to repeat (append-once
  output keyed by item id).

## 7.5 Phases

Each phase compiles, runs and is useful on its own.

### Phase 0: prerequisites from this audit

A multi-hour run multiplies every per-turn defect. Fix first:

| Item | Why it blocks runs |
|------|--------------------|
| C1, C2 | A chat that hits its limit can stay stuck; a run's parent chat will hit it. |
| L1, L2 | On a self-hosted model every segment would re-read its whole prompt, and background calls would compete with the run for the slot. |
| L3 | Thousands of tool calls, each paying an approval round trip through Kitty. |
| M4 | Pathway would learn "about the user" from hours of worker transcripts. |
| B2 | A second window sending into the run's chat would mark the live turn as failed. |

**Done when:** a 30-step turn on a self-hosted model shows cached tokens close to prompt tokens on
every step after the first, and auto-approved tool calls no longer pause.

### Phase 1: the ledger and its tools (engine)

- Migration `032_runs.sql`: `runs` (id, app_id, session_id, goal, status, reason, budgets,
  counters, output_path, created/updated) and `run_items` (run_id, item_id, description, status,
  attempts, result, updated_at), with an index on `(run_id, status)`.
- `storage/runs.rs`: create, get, list for app, add items, claim next N, complete, fail,
  counters, and `requeue_doing_on_boot` (the item-level counterpart of
  `jobs::mark_interrupted_on_boot`).
- Loop-only tools, offered only inside a run's segments (same mechanism as `load_tool_group`
  and `request_more_steps`): `run_plan` (add items), `run_next` (claim up to N), `run_done`
  (record a result), `run_fail` (with a reason), `run_status`.
- Routes: `POST /api/runs`, `GET /api/runs`, `GET /api/runs/{id}` (with items, paged),
  `POST /api/runs/{id}/pause`, `/resume`, `/cancel`. All scoped like `/api/jobs`.
- Plan confirmation: run statuses `planning`, `awaiting_approval`, `running`, `paused`,
  `stalled`, `done`, `cancelled`. `run_plan` moves a run to `awaiting_approval` and ends the
  planning segment. `POST /api/runs/{id}/plan` takes `{decision: approve | revise | cancel,
  items?, note?}`: `approve` (optionally with the user's edited item list) starts execution;
  `revise` runs another planning segment with the note. During `planning` the segment's tool
  list excludes write-class tools and the other `run_*` tools.
- Model-initiated start: `start_long_horizon(goal)` is offered on ordinary turns of an app that
  has runs switched on. Calling it creates the run in `planning`, ends the current turn, and
  emits `run_state` so the client shows the card.

**Done when:** a test creates a run, plans 50 items through the tools, completes them out of
order, restarts the engine mid-way, and finds no item lost or completed twice; and a run in
`awaiting_approval` executes nothing until `approve` arrives, including across a restart.

### Phase 2: the driver (engine)

- `agent/run_driver.rs`: one task per active run. Loop: build the segment prompt from the ledger,
  call `run_turn_and_wait` on the run's session, read the ledger, decide.
- Segment prompt builder: head, goal, ledger summary, the instruction "claim items with
  `run_next`, record each with `run_done`, stop when none remain". Kept byte-stable at the front
  so the prompt cache helps from segment to segment.
- Budgets on the run, each optional: wall clock, total tokens, segments, per-item attempts.
  The token budget is sent by the app when the run is created (and can be raised on a paused
  or stopped run with `PATCH /api/runs/{id}`), so changing Kitty's default never needs an
  engine restart. Tokens are counted across the planning segment, every execution segment and
  every worker. A run that reaches its budget stops with status `paused` and reason
  `token_budget`, keeping its ledger, so the user can raise the budget and resume.
  The wall-clock limit is supplied and adjusted the same way. The driver checks it between
  items and between segments, never mid-item, and measures only time spent in `running`.
- Stall rule: two consecutive segments with no item changing status stops the run with status
  `stalled` and the last model message as the reason.
- Events on the app stream: `run_progress` (counts, current item, tokens), `run_state`.
- Approvals: a run carries a granted scope chosen at start (folders, and whether shell is
  allowed). Anything outside it follows the scheduled-run rule: wait, then deny, and record the
  item as failed with that reason, so one prompt cannot hold up the other 79 items.

**Done when:** a run of 40 trivial items completes across several segments with no user
input, on a model whose window fits about 8 items per segment; and a run whose tool always fails
stops as `stalled` within two segments.

### Phase 3: workers by default for collection items

- A `per_item` execution hint on the run: the segment calls a specialist with fan-out over the
  claimed items instead of doing them inline. Reuses `per_ref` fan-out and its limits.
- A built-in specialist for "find, read and annotate one source" with a strict answer schema
  (citation fields, annotation, source URL, confidence), tool allow-list of web and document
  readers only.
- Worker results go straight into `run_done`; page content never enters the parent context.
- Workers feed Memorabilia. Today neither memory pass runs for a delegate
  (`agent/loop_.rs:4166-4174`), on the grounds that the parent's turn brings in anything worth
  keeping. In a run that is no longer true, since the parent never sees the pages. So for
  workers of a run, the Memorabilia harvest does run over the documents the worker brought in
  (scraped pages, downloaded files), attributed to the *run's parent chat* so recurrence is
  counted against the chat the user knows. Intake is unchanged: paragraphs are still
  pre-filtered and screened, and only what recurs is promoted overnight. Pathway learning stays
  off for workers and for run segments (M4), because those transcripts are not the user
  speaking. Memorabilia is desktop-only, so on Android this step does nothing.
- On a one-slot server the fan-out width is 1 (already how `completable_fan_out` behaves); the
  run is slower, not different.

**Done when:** the bibliography example produces 80 entries, the parent session's largest
prompt stays under half the window throughout, and total tokens across workers exceed one
million.

### Phase 4: checkpoint inside a segment

Replaces "wrap up" with "checkpoint and continue" for segments of a run only; ordinary chat turns
keep the wrap-up valve.

- When projected input crosses the wrap-up threshold inside a run segment: ensure every finished
  item is recorded, end the segment early with reason `checkpoint`, and let the driver start the
  next one. This is deliberately a segment boundary, not an in-place rewrite of the message
  list, so the tool loop's invariants (tool-call pairing, token hints, persistence) are
  untouched.
- Mask older tool results within a segment more aggressively than in chat, since results that
  matter are already in the ledger.

**Done when:** a segment forced over its threshold ends cleanly, the next segment starts within
a second, and no item is repeated.

### Phase 5: Kitty surface

- Rust: `bigtiny/runs.rs` and `commands/runs.rs` over the new routes; `run_progress` and
  `run_state` forwarded as `run://progress` and `run://state` (payloads carry `session_id` and
  `run_id`, per core rule 2).
- A run card in the chat it belongs to (`components/chat/RunCard.tsx`, shared by overlay, hub and
  Android): goal, items done of total, current item, tokens and time used, Pause, Resume, Cancel,
  and an expandable item list with each result. Colours and spacing from theme properties only.
- Starting a run, two ways. (1) `/longhorizon <request>`: handled in `Composer.tsx` beside
  the existing `/compact` check (around line 129). Unlike `/compact`, which must match exactly,
  this is a prefix: the command must be the first token, followed by a space and a non-empty
  request, so a message that merely mentions it is sent as normal text. Attachments on the
  message go with the run. (2) Model-initiated: the engine's `run_state` event arrives and the
  card appears with no client action.
- Plan review, modelled on Claude Code's plan mode: when a run reaches `awaiting_approval` the
  card shows the approach and the item list, editable in place, with **Approve**, **Revise**
  (with a note to the model) and **Cancel**. The same card sets the granted scope (folders,
  whether shell is allowed) and shows the token budget that will apply, both changeable before
  approving. If no Kitty window is showing it follows the approval path already used for tool
  approvals: notification, and the overlay summoned.
- Visible segments: segments render through the existing chat components as ordinary turns.
  Add a per-segment collapse row in `MessageList` for finished segments of a run (keyed off a
  `run_id` and segment number carried on the turn's events), expanded for the one in progress.
- Token budget setting: `Settings → Advanced → Long-horizon token budget`, a number field with
  a "no limit" option, stored in Kitty's config (`long_horizon.token_budget`) and sent on
  `POST /api/runs`. It is the default for new runs; the plan-review card can override it per
  run. Not part of `SpawnSnapshot`, so changing it restarts nothing. For hosted providers the
  field cannot be set to "no limit".
- Wall-clock limit setting: `Settings → Advanced → Long-horizon time limit`, in hours and
  minutes with a "no limit" option, stored as `long_horizon.wall_clock_secs` and sent on
  `POST /api/runs` alongside the token budget. Same rules: default for new runs, overridable on
  the plan-review card, raisable on a paused run, restarts nothing. The clock counts time the
  run spends in `running` only; time waiting for plan approval, paused, or waiting on a tool
  approval does not count. A run that reaches the limit finishes the item in hand, then stops
  as `paused` with reason `time_limit`, ledger intact. "No limit" is allowed for self-hosted
  providers, since the token budget and the stall rule still apply.
- Tray and notifications: reuse the Working state; notify on finished, stalled, or approval
  needed.
- Android: the turn service must span the run, not each segment, and the one-hour wake lock
  needs renewing. See B4.
- Settings → a "Runs" list with history, like scheduled-task runs.

**Done when:** on Windows and Android, a run started with `/longhorizon` in the overlay shows
its plan for approval, executes nothing before Approve, can be watched segment by segment in a
hub window, paused, resumed after quitting and reopening Kitty, and cancelled; a run the model
started itself behaves identically; a run stopped by the token budget or the time limit
resumes after that limit is raised; time spent awaiting plan approval does not count toward
the time limit; lint and both clippy targets are clean.

### Phase 6: verification and finish

- When the ledger has no open items the driver runs one verify segment in a fresh context: read
  the output against the goal and the ledger, list gaps and duplicates. Gaps become new items
  (bounded to one extra round by default); otherwise the run completes.
- The final message in the chat is a short summary with a link to the output file, which appears
  in the artifacts pane as usual.

**Done when:** deliberately removing five entries from the output before verification causes
exactly those five items to be re-queued.

## 7.6 Risks

| Risk | Mitigation |
|------|------------|
| The model ignores the ledger and works inline | The segment prompt and tool descriptions make the ledger the only way to finish; the stall rule catches a model that never records progress. Test with the smallest model Kitty supports. |
| Runaway cost on a hosted provider | Token and wall-clock budgets are required when the provider is hosted; the specialist model denylist already applies to workers. |
| Repeated side effects after a restart | Item-level resume, attempt counts, and append-once output keyed by item id. |
| A shared engine restarted by another app mid-run | Runs resume on boot from the ledger; the engine already refuses a restart while a turn is active. |
| Single-slot servers starve interactive chat | Run segments use `Priority::Background`; an interactive turn goes first (and see L2 for in-flight calls). |
| Memory pollution | Pathway learning is off for segments and workers (M4). Memorabilia does take in workers' sources, by decision; its existing intake screen and recurrence rule are what keep one run's reading from flooding long-term memory. Watch the candidate count after the first real runs, and fix M1 first so reinforcement keeps up. |
| The model starts long-horizon mode too eagerly, or never | The tool description states when to use it (work that will not fit one turn: many sources, many files, hours). Plan confirmation makes an unwanted start cost one Cancel click. `/longhorizon` covers a model that never offers it. Track how often model-started plans are cancelled. |
| A very long visible transcript slows the chat | Finished segments collapse to one row; the message list is already virtualized past 200 messages. Resume (section 2, E4) must return the transcript in one call before runs make chats this long. |
| A plan left unapproved holds a run open indefinitely | `awaiting_approval` holds no model slot and no wake lock; it is a row in a table. Show it in the Runs list and on the tray like a pending approval. |

## 7.7 Decisions made

| Question | Decision |
|----------|----------|
| Are a run's segments visible? | Yes. Segments are ordinary turns in the chat, collapsed to one row each once finished. |
| Is the plan confirmed before work starts? | Yes, in the manner of Claude Code's plan mode: a read-only planning segment, then Approve, Revise or Cancel, with the item list editable. |
| Where is the token budget set? | `Settings → Advanced`, as the default for new runs; overridable per run on the plan-review card; sent to the engine per run, never as a start-up setting. |
| Where is the wall-clock limit set? | Also `Settings → Advanced`, with the same override and resume behaviour. It counts running time only and stops the run between items. |
| Do workers' sources feed Memorabilia? | Yes, through the normal screened intake, attributed to the run's parent chat. Pathway stays off for runs. |
| How does long-horizon mode start? | The model may start it with `start_long_horizon`, or the user forces it by beginning the message with `/longhorizon`. Both lead to the same plan confirmation. |

Still open: the *default values* for the wall-clock limit and the segment cap on self-hosted
providers, where tokens are free but time is not.

## 7.8 Order and size

Phase 0 is fixes already described in this file. Phases 1 and 2 are the minimum that ends
re-prompting and can ship behind a setting with a plain progress line. Phase 3 is what makes
millions of tokens practical. Phase 4 is the most delicate and is intentionally designed as a
segment boundary to keep it small. Phases 5 and 6 can proceed alongside 3. Record the phases in
`docs/BACKLOG.md` and the new routes in `BigTinyV2/API.md` when work starts.
